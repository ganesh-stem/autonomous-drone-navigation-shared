# web3d_drones_edge_residual_adaptive_motion

Ideas 1–3 of `study_guide/part5_appendix/A5_research_ideas.md`, built on `../web3d_drones_edge_residual_adaptive` (the base code, unchanged apart from a `flyer_speed` factor in `flyers.py`).

| Idea | What it does here | Where |
|---|---|---|
| 1. Motion cues | 28 extra inputs: how much each ray reading changed since the last step (65 inputs instead of 37). Zero after a start or respawn. | `motion_cues.py` |
| 2. Reward and curriculum for moving obstacles | Approach penalty (up to 0.5 per step) for a near obstacle closing faster than the drone's own flight explains; flyer speed ramps from 0.4 to 1.0 over the first half of the run, plus the base's gale ramp. Evaluation is always at full speed with the penalty off. | `motion_cues.py`, training loop |
| 3. Evolved prior | The fixed goal rule is now a 12-number function with avoidance terms (`prior.py`). A separable CMA-ES (`evolve_prior.py`) tuned the numbers by flying the prior alone among the roaming flyers. The network still learns the residual. | `prior.py`, `evolve_prior.py` |

## Files

- `edge_v3_16_residual_adaptive_motion_sac.py` — the **Kaggle standalone trainer** (one file, numpy + torch). Generated by `build_trainer.py`; paste into a Kaggle cell (GPU on). Settings block at the top: `motion_cues`, `approach_penalty`, `flyer_ramp`, `prior='evolved'|'classic'`, `warm_start=...`. With `motion_cues=False, approach_penalty=0, flyer_ramp=False, prior='classic'` it behaves like v3_12, so the three ideas can be compared one by one.
- `build_trainer.py` — regenerates the trainer from the base trainer and the modules (embeds `results/evolved_prior.json`).
- `server_edge_residual_adaptive_motion.py` — viewer, `python server_edge_residual_adaptive_motion.py`, http://localhost:8023. Imports the base server; brains: the Kaggle brain (`results/models/sac_motion/brain_final.pth`, if present), evolved prior only, classic prior only, and the base brain.
- `tests/selftest_motion.py` — 31 offline checks (`results/selftest_motion.txt`).
- `results/` — `evolved_prior.json`, `evolve_log.csv`, `evolve_stdout.txt`.

## The evolution result (honest numbers)

40 generations × population 16, each candidate flew 5 episodes of 1,500 steps; score = goals/1k − 2 × collisions/1k. Held out on 6 new skies × 3,000 steps, prior alone (no network), moving flyers:

| prior | goals/1k | collisions/1k |
|---|---|---|
| classic (old fixed rule) | 3.67 | 444.2 |
| evolved (last-generation best, picked) | 5.56 | 53.8 |
| evolved (final mean) | 6.17 | 70.8 |

So evolution cut the prior's collisions about 8×, but the prior alone still hits obstacles and is slow to reach goals; it is a better starting point for the network, not a finished pilot. Whether that helps the trained brain is **not measured yet**.

## A real PID controller (`pid_controller.py`, `evolve_pid.py`)

The "PID" in the residual trainers is not a PID: `pid_bias` is a dead-band rule (climb / descend / turn / straight from the sign of the goal error) with no integral, no derivative and no gains. `pid_controller.py` is a real one:
three loops (yaw, altitude, speed), each `u = kp·e + ki·∫e + kd·de/dt` with a filtered derivative and anti-windup. Yaw error is the bearing to the goal (plus an offset away from the nearer side when something is ahead), altitude error is the goal's height
above the drone (plus an offset to the freer side), the speed setpoint drops as the front gets blocked. The continuous demands (turn rate, climb rate, speed) are rounded to the nearest of the 9 discrete actions, because the environment only accepts those.
It is a standalone policy: it needs memory (the integral and the last error), which the SAC replay buffer does not store, so it is **not** wired into the learner. It is a brain of the viewer (`real PID (tuned gains)`), and `python evolve_pid.py` tunes its 12 numbers with the same CMA-ES.

Held out (6 new skies × 3,000 steps, moving flyers, controller alone, no network):

| controller | goals/1k | collisions/1k |
|---|---|---|
| old dead-band prior | 4.6 | 393.6 |
| evolved prior (`prior.py`) | 4.6 | 120.6 |
| real PID, default gains | 7.6 | 96.3 |
| real PID, tuned gains (25 generations) | 3.5 | 82.3 |

These runs are small and noisy (the same evolved prior scored 54 collisions/1k on a different set of skies), so read them as "the same order of size". The real PID with its default gains is already about as good as the evolved prior, and the short tuning
bought fewer collisions at the price of fewer goals; it did not clearly beat the defaults. A longer tuning with more episodes would be needed to say more. `tests/selftest_motion.py` checks the P, I and D terms, the anti-windup and a simple closed loop.

## Kaggle notebook: train 15 minutes, render a 5-minute video (`kaggle/`)

`kaggle/drone_motion_on_kaggle.ipynb` (same layout as the kart notebook: get the code with a `GITHUB_TOKEN` secret or a dataset, install, train, render, keep): it trains `edge_v3_16_residual_adaptive_motion_sac.py` for 15 minutes
(plus a short evaluation, about 2 min), then `kaggle/render_flight_video.py` flies the trained `brain_final.pth` for 5 minutes in real time and draws it to an MP4 (1280x720, 30 fps; about 10 minutes of compute, tested here at roughly 1.8 s of compute
per second of video on 4 CPU cores). Rebuild the notebook with `python kaggle/make_notebook.py`.

The video is recorded with the **real three.js viewer** (`kaggle/record_viewer_video.py`, the idea of the kart notebook's `record_video.py`): a headless Chromium opens the viewer page, a stand-in WebSocket and a virtual clock let the script feed it
one exact frame at a time (state, obstacles, targets, traffic, roaming flyers built from the torch-free world), and every frame is screenshotted into ffmpeg. So the video shows the live viewer: city, gates, birds and patrol drones, traffic, weather, day / dusk / night, side panel.
It needs WebGL: with a GPU (Kaggle T4) the kart notebook got about 10 frames/s at 720p; with software rendering it is about 1-2 frames/s here, far too slow for 5 minutes, so the notebook has a fallback, `kaggle/render_flight_video.py`, a much simpler numpy + OpenCV chase-camera renderer
(a different look, which is **not** the viewer). `--brain evolved|classic|pid` renders the prior alone or the real PID without any training.
Tested here: a 6-second clip with the real viewer in software GL (frames checked by eye), the OpenCV fallback, the message builders and the notebook file (self-test). Not tested here: the GPU route on Kaggle, the notebook run on Kaggle, and the trainer's `main()` (no torch in this sandbox), so the first notebook run is the first real run of the trainer.
