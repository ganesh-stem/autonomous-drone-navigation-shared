# Issues met while building ros2_edge_residual_adaptive, and how each was fixed

The issues of `ros2_edge_drone/ISSUES_AND_FIXES.md` (WSL virtual environments, the light cycle, the MAVLink lost counter, the 400 steps/s limit) apply here too, because the nodes are the same code. This list is only what was new.
Nothing below was found by running under ROS 2 (it was not available): add your first-run findings at the bottom.

| # | What happened | Cause | Fix |
|---|---|---|---|
| 1 | `core.py` of `ros2_edge_drone` would have given a different sky than the server (50% towers, more obstacles) | it was generated before the sources changed (`TOWER_PROB` 0.5 -> 0.38) and the viewer server patches the obstacle density (`D.COUNT_PROBS`) at start-up | `tools/build_core.py` regenerates it from the current sources and patches `COUNT_PROBS` to the server's value; it stops with an error if that line is ever not found. The world was then checked step by step against the server's (identical) |
| 2 | The old ROS bridge would have left holes in the new viewer's HUD (Total goals, Total collisions) | the new viewer reads `totalGoals` and `totalCollisions`, and shows goals and steps since the last weather change | `web_bridge` sends them (totals from the status, "since the weather change" values from the KPI node), `replay_lib` too. The self-test reads `hud()` in `web/js/ui.js` and fails if the message misses any field it uses |
| 3 | `colcon build` would have failed on the viewer | `setup.py` listed `glob('web/*')`, which now contains the `js/` folder, and a directory cannot be installed as a file | files and `web/js/*.js` are separate entries in `data_files` (the list was checked: 1 launch file, 2 weights, 2 web files, 12 modules) |
| 4 | Exporting the brain needed torch | the checkpoint is a torch zip file | `tools/export_residual_npz.py` reads the zip and rebuilds the tensors with a small unpickler (numpy only). It was run on the real checkpoint |
| 5 | The optimised policy is not bit-identical to the straightforward one | different matrix layout changes the order of the sums | the docs say so: logits equal to within 1.5e-5 (largest difference in the self-test), the same action on every state tried. (The first version of the docstring claimed "same arithmetic": corrected) |
| 6 | The first self-test crashed: "truth value of an array is ambiguous" | the test filled the bridge's rays by hand with `array and ...` | a test bug. The bridge gets its rays over the bus, as in the real system, and the test checks that they arrived |
| 7 | A `shield` option that did nothing | this brain ignores the safety mask | the option and the `/shield_mask` topic were removed from `sim_node` and the launch file |
| 8 | Buildings stood on the roads and sidewalks of the viewer | the world places a tower anywhere in its 250 x 250 chunk, up to the border, and the viewer's roads run along the chunk borders | towers are shifted (not resized, no extra random numbers) to stay 18 units inside their chunk: in `server_edge_residual_adaptive.py` for the server and by `tools/build_core.py` for the ROS `core.py`. The self-test checks the distance of 364 towers |
| 9 | After that shift the two worlds differed by 3e-15 in one sensor value (positions identical) | the server's copy recomputed a tower's width from its two edges, the generated code used the original width, so the last bit differed | both do `(x0 + w) - x0` first. The self-test, which compares the two worlds step by step, caught it |

| 10 | The cars were only drawn by the viewer, so the camera and the detector could not see them (they saw random "vehicles") | traffic lived in the browser | the traffic and the parked cars moved into `city_world.py` (shared by the server and the ROS `sim_node`, published on `/edge_residual/traffic`); the camera scene uses them and the viewer only draws what it receives. The self-test checks that the camera above a road and above a car park counts the cars that are really there. Limit: the trained detector itself was not run here, only the camera's ground truth counts and image contain the cars |
| 11 | The viewer's birds and patrol drones were decoration: they wandered anywhere while the simulator knew only static boxes | the viewer roamed them by itself | `flyers.py`: every floating block sends out birds and patrol drones, each a small roaming box whose position is a pure function of its block, its number and the step number; the simulator, the camera node and the viewer all compute the same positions from the step number (`/edge_residual/flyers` carries it). The gates and the static floating blocks are unchanged. Check 8 of the self-test compares simulator, camera and viewer. The shipped brain (trained on a static world) mostly flies around them (0.48 collisions per 1k steps, `tools/eval_moving_obstacles.py`) |
